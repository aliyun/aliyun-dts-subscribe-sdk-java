# DTS 通道内部恢复位点

适用范围：`com.taobao.drc.client.network.dstore.SubscriptionConsumer`。不适用于另一套 `com.aliyun.dts.subscribe` consumer 的位点持久化规则。

## 空拉取

超过 `socketTimeOut` 没有收到数据时，SDK 仍向 CM 检查通道。CM 明确返回 DTS 时保留当前 TogoConsumer 和读取位置继续 poll；明确返回 DRC 时保留原有通道切换流程。1.1.20 中，请求异常、不成功响应、无效或缺失的通道类型均保留已知通道，不再把探测失败当成切换 DRC。尚无已知通道的首次发现保留历史默认行为。首次空 poll 不会因计时器为 0 而立即触发检查。

## 明确异常后的恢复

OffsetOutOfRange、集群变化等明确异常仍会重建底层消费者。完整 consumer 重建前的 CM 通道注册和重建后的时间戳定位采用同一规则：

- 多分片模式及 1.1.20 的单服务模式：优先使用对应 `CheckpointManager.saveCheckpoint`，即通过 `Record.ackAsConsumed()` 推进的安全时间戳。
- 还没有确认位点：使用该 shard 最初的启动时间戳。不能因为收到较新的心跳就越过未确认记录。
- 单服务模式在 1.1.19 未维护 ack 队列，1.1.20 改为跟踪已交付记录；不需要新增位点提供接口。未调用 ack 时仍保守使用起始时间戳，不能将最新心跳视为业务处理完成。为兼容不调用 ack 的旧用户，单次消费批次最多跟踪 10,240 条未确认记录；超过上限会释放队列、记录 WARN，并将恢复位点冻结在最后确认位置，直到消费者重建。不会跳过未跟踪的数据，但可能增加重放；需要监控并确保及时完整地确认。
- 找不到安全时间戳对应的 offset，或该时间戳早于可用数据范围时，报错退出该次定位，不静默跳到最新位置。

调用方应在记录实际处理完成后，对 SDK 交付的原始 `Record` 调用 `ackAsConsumed()`，而非只入异步队列后就 ack。交付的 BEGIN、COMMIT、心跳等记录也须按处理顺序确认，不能只确认部分 DML。未确认记录会阻碍位点推进。事务内记录沿用现有的事务安全时间戳规则，恢复可能重放已处理的部分事务或同一秒的数据，因此调用方仍需支持重复处理。乱序和重复 ack 不会越过仍未确认的前置记录，但可能使保存位点保守滞后。

每次重建会冻结本次恢复时间戳并建立独立的待确认队列。1.1.20 在 CM 注册前冻结时间戳并隔离旧批次确认；新消费者定位复用同一快照，避免注册和 seek 之间的迟到 ack 改变定位。旧批次迟到的 ack 不会推进新批次的 shard 位点。未交付缓存、事务状态按消费批次隔离；未确认的数据从安全位点重新读取。

心跳仍更新原配置 checkpoint 供现有诊断使用，但该字段不再是 DTS 内部恢复的唯一依据。保存的 ack 位点是进程内状态；进程整体重启仍须由调用方提供持久化的安全起点。本次修改不改变 DTS/DRC 跨通道状态迁移逻辑。

## 1.1.20 升级注意

使用 `startService()` 且已经在处理成功后确认所有交付记录的用户，只需升级 SDK 即可使用确认位点进行 DTS 内部重连；不调用 ack 的用户升级后不会自动获得较新的恢复位点。不能以本次修复保证真实 DTS/DRC 跨通道切换、进程重启或错误提前 ack 的数据安全，业务仍须保留持久化安全位点及重复处理能力。

