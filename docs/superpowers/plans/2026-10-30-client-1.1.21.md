# Client 1.1.21 Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan inline, followed by one independent whole-change review.

**Goal:** 发布准备状态的 1.1.21：单订阅回调成功确认、多订阅逐条 ACK，修复恢复与生命周期，并沉淀文档。

**Architecture:** 启动方法决定完成契约，通道决定恢复协议。CheckpointManager.Recovery 同时承载 DRC/DTS 的连接代次；单订阅确认不可变批候选，多订阅使用压缩 ACK 区间。主客户端保留安全状态，协调失败、重连和 reset。

**Tech Stack:** Java 8、Maven 多模块、JUnit 4、Netty、现有 Kafka consumer。

**Spec:** `docs/superpowers/specs/2026-10-30-ack-compatibility-design.md`

## Global Constraints

- 不新增 ACK 模式参数或替代选择接口；保持既有公开方法及序列化兼容。
- startService 在 DRC/DTS 都以整批 notify 成功返回为完成，公开 ACK 为 no-op。
- startMultiService 在 DRC/DTS 都逐条 ACK，不受实际分片数量影响。
- 只兼容旧 DRC 和历史散列订阅，不保留 1.1.19/1.1.20 单订阅异步 ACK 契约。
- 版本 1.1.21；不发布远端、不提交；保留当前工作区已有修改和无关文件。

## Review Focus

- 用户在回调中 ACK、修改 Record/列表后抛异常，不得提前确认单订阅。
- 心跳缓存未交付、或已确认区间右端不是心跳，DRC 恢复不得越过缺口。
- 后台 ACK 触发预算溢出时，没有新的源数据也应使拉取线程退出。
- 回调内 stop、并发 stop、join/reset/start，不能死锁、启动旧代次或重置安全位置。
- 通道或分片拓扑变化，不得使用收到但未确认的位置代替安全恢复点。
