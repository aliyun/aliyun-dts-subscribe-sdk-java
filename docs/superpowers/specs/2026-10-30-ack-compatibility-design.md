# ACK 与恢复位点的兼容性修订方案

日期：2026-10-30。目标版本：1.1.21。状态：本地候选实现，未发布；真实 DRC/DTS 协议验收待执行。

用户明确要求不新增 ACK 模式配置。本修订删除上一版的模式参数和相关选择接口，
使用现有启动方法和 ackAsConsumed；不以新 setter、Listener
类型或其他参数变相增加模式选择。用户进一步限定：只兼容旧 DRC 用法及历史散列
订阅，不要求兼容 1.1.19/1.1.20 的过渡行为。真实协议验收仍待执行。

本设计已完成独立设计审阅，并在现有工作区实施。用户使用约束、参数和升级方式见
[1.1.21 使用与升级说明](../../CLIENT_1.1.21.md)，实施与验证记录见
[执行计划](../plans/2026-10-30-client-1.1.21.md)。本地回归不代替真实服务端验收；不自动提交或发布。

## 1. 已确认的契约和问题

- [旧详细手册](https://code.alibaba-inc.com/AliDB/DRC-gitbook/blob/patch-7/Arch/client.md)
  的单订阅示例没有显式 ACK，DRC 内部重连使用 heartbeat timestamp。
- [集团订阅客户端使用说明](https://aliyuque.antfin.com/dts/public/icfn6l) 明确规定
  `startMultiService()` 多 subTopic 订阅消费后逐条 ACK，覆盖旧 DRC/DStore 统一
  Client `2.2.2.58.*.hash`。不能把这个要求扩大到历史单订阅。
- 1.1.20 基线的 DRC 单订阅不入 ACK 链表；DRC 多订阅入链，ACK 推进供
  `getMultiSafeTimestamp()` 汇总的位点，但其自动重连仍使用各分片的心跳。
- 1.1.20 DTS 单订阅已经依赖 ACK 确认恢复位置，实际存在 notify 入异步队列、
  后台处理后 ACK 的用户。按用户最新要求，这一过渡行为不作为本方案兼容约束。
  修订后单订阅以回调成功返回为完成判据，必须明确告知这个变化。
- 当前 notify 抛异常后，handleException 正常返回会吞掉异常，后续心跳继续推进。
  SDK 缓存未交付时也会更新心跳。resetService 是空实现，旧的同实例重启循环失败。
- 原 10240 上限导致永久静默冻结；上一轮改成压缩 ACK 区间并移除默认条数上限，
  但显式区间预算溢出仍继续投递，应进一步调整。

代码入口：RecordNotifyHelper、CheckpointManager、DRCStoreClientImpl、
DStoreClientImpl、AbstractStoreClient、DRCClientImpl、RecordsCache。

## 2. 目标与取舍

保证正确性优先：恢复位置不得越过相应协议允许的安全边界；允许重放，不保证
业务 exactly-once。旧 DRC 同步单订阅能够不改处理循环；旧多订阅继续逐条 ACK。
所有实际通道采用一致的调用契约：单订阅以 notify 成功返回为完成，多订阅逐条
ACK。不要求保留 1.1.19/1.1.20 的 DTS 单订阅显式 ACK 契约。

无法自动区分 notify 返回代表“处理完成”还是“仅入队”。不根据第一个 ACK、
一段时间没 ACK、ACK 比例等启发式切换确认模式。不能承诺所有历史用户在所有
消费写法下零改动且恢复语义完全一致；以用户已经选择的启动方法确定完成契约，
不再保留按 DRC/DTS 通道变化的确认要求。

业务进程重启仍需用户持久化确认位置；SDK 内存状态不代替业务事务或持久化。
不自动跳到最新位置，不自动跳过失败记录，不擅自撤销已发生的业务副作用。

## 3. 固定规则，不增加确认模式接口

| 当前运行方式 | 完成与恢复判据 | ACK 行为 |
|---|---|---|
| DRC + startService | 保留心跳恢复；心跳所在批次成功交付后才可推进 | 不新增 ACK 要求；调用 ACK 安全无操作 |
| DTS + startService | notify 成功返回后的整批完成边界及事务安全位置 | 不要求 ACK；调用 ACK 安全无操作，不得提前确认 |
| DRC + startMultiService | 已 ACK 前缀内的心跳恢复边界 | 保持历史逐条 ACK 要求 |
| DTS + startMultiService | 各分片已 ACK 前缀及事务安全边界 | 保持历史逐条 ACK 要求 |

确认规则仅由现有启动方法决定，固定在根客户端的订阅会话中，不能由实际通道、
subTopic 数量、第一个 ACK 或等待时长改变。startMultiService 即使只得到一个
subTopic，仍按逐条 ACK 处理。跨通道重连保留启动方式和完成判据。

单订阅中，SDK 在进入 notify 前捕获整批的不可变恢复候选；回调正常返回后一次
确认整批。不是在业务回调中代替用户逐条调用公开 ACK 方法。用户提前或重复调用
record.ackAsConsumed() 都不能绕过回调成功返回这个条件。整批中途失败则不推进
本批恢复边界，重放可能重复已执行的部分，业务仍须具备重复处理能力。

多订阅 ACK 针对每条原始记录，包含心跳和事务标记，不表示批末累计确认。
notify 返回不自动确认；批内已明确 ACK 的成功记录可保留确认，其余不能因回调
返回或超时被确认。允许异步和乱序 ACK，恢复不得跨过未确认缺口。

旧 DRC 同步单订阅示例不改消费循环，落到 DTS 后也不需要额外 ACK，确认位置
随成功返回的批次推进；旧散列订阅继续处理成功后逐条 ACK，无须识别实际通道。

单订阅若内部使用线程池，可以并行处理，但必须在 notify 返回前等待本批业务
成功完成。仅入队就返回不满足单订阅完成契约，之后补 ACK 不能使本批回退。
这是明确的使用约束，不能宣称兼容 1.1.19/1.1.20 单订阅的异步 ACK 用法。既有
多订阅接口仍支持回调返回后异步 ACK；不要求用户为所有普通同步消费学习新接口。

## 4. 位点管理

### 4.1 拆分三个概念

1. received：已经读取/解析到的位置，仅作观测，不能直接当成消费完成。
2. confirmed：依照上表完成判据形成的连续完成范围。
3. recovery：从 confirmed 前缀中选出的、适用于目标存储协议的恢复边界。

每个逻辑 subTopic 独立维护代次、交付顺序和协议边界；多订阅额外维护 ACK 前缀
及已确认区间。单订阅不为业务显式 ACK 创建 pending 链表或乱序区间。
顺序以交付序号为准，禁止通过 max(timestamp) 判断推进；源时间戳可能回退。
所有已交付类型均参与确认，包括 BEGIN、COMMIT、ROLLBACK、DDL、心跳。

### 4.2 DRC

保留 DRC heartbeat timestamp 的恢复语义，不直接替换成任意 DML timestamp。
单订阅中，心跳先形成候选恢复边界，只有所在交付批次 notify 正常返回，且此前
没有失败回调，才能更新重连位置；不等待 ACK，不赋予异步业务完成保证。
多订阅中，心跳及之前的记录均逐条 ACK 后，才能用于重连。因此 DRC 多订阅
自动重连也真正受业务确认约束，修复 ACK 与重连位置脱节。

尚无合格心跳时使用该代次的安全恢复起点；不会以最新 received 心跳兜底。
长时间无合格心跳可能增加重放，要暴露恢复位置的停滞状态，不能虚构进度。

### 4.3 DTS

单订阅从成功返回批次中捕获的最后安全边界推进；多订阅从已 ACK 连续前缀推进。
事务安全位置的计算保持一致。CM 注册和 seek 使用同一份冻结恢复快照。不能用 received 心跳
覆盖未确认缺口，不能用未确认 Kafka offset 绕过安全恢复边界。

### 4.4 跟踪结构

单订阅每个分片只保存当前交付批次的不可变候选和最后完成快照，不保留无限增长
的 ACK 状态。候选在回调前捕获，不能依赖回调后可能已被业务修改的列表或 Record。
批次完成和连接代次失效在同一锁规则下线性化；失效后的成功返回不推进新代次。

保留上一轮序号凭证与 ACK 区间合并的方向，并推广到 DRC 多订阅，以避免 manager
长期持有业务 Record。凭证包含所属逻辑分片、代次、序号、捕获的协议元数据、
ACK 状态。区间元数据保留其右端安全位置和区间内最后一个心跳候选；区间合并
必须保留心跳，即使右端是 DML。全不 ACK 时不为每个未确认记录保存 manager 节点。

不改变 Record 既有序列化 UID；新状态 transient。保留旧方法签名，prev/next
不再作为业务判断 ACK 是否适用的契约。重复 ACK、未注册 ACK、旧代次 ACK 安全
无操作；异步 ACK 和重连快照冻结在同一锁规则下线性化。

### 4.5 缓存与连接代次

缓存中的记录尚未交付，不得确认其中的心跳。代次失败后丢弃该代次未确认缓存，
从冻结安全位置重放；不能把旧缓存与新连接的记录混在同一事务状态中。
新连接先隔离旧代次，旧回调/旧 ACK 不再推进新代次位置。已经进入业务回调的
外部副作用不能撤销；业务异步任务跨重连完成时可能与重放重复，须由业务幂等处理。

## 5. DRC/DTS 切换和分片拓扑

根客户端保存当前通道、启动方式、原始启动位点和恢复状态快照。替换 StoreClient 前完成
旧连接停投递、冻结快照与代次隔离；不能以新的空 manager 或可变 received 位点
代替已确认的恢复状态。相同物理/逻辑分片的普通重连按各自安全快照恢复。

跨通道不复用 Kafka offset、DRC position 或投递序号。首版的确定性保守行为：
只在协议与逻辑分片映射经过明确验证时转移可移植恢复边界；在没有这项验证的
当前仓库中，不启用该优化，回退到根客户端保存的原始、可用于目标协议的启动
时间戳，并输出显著的回退事件、起点和原因。原始起点只有物理 position、没有
目标协议可用时间戳时，终止并报不可迁移，不能猜测时间或使用最新心跳。

源数据不再保留时清晰报错。这个选择可能造成较大重放，但不会无依据跳过数据；
必须把跨通道回退和 ACK 停滞区分开。实现同源时间戳/分片映射验证后才缩小重放。
拓扑新增、删减、重分片同样不把未知分片从汇总中忽略；不能证明映射时按上述
保守恢复路径处理。`getMultiSafeTimestamp()` 保持原聚合含义，不把某个快分片
最后一条 record.getSafeTimestamp 当作整个订阅的安全位置。

## 6. 异常与生命周期

- notify 失败先标记该代次失败、禁止后续交付和位置更新，再调用 handleException
  作为通知，随后将原异常传回重连层。handleException 返回不等于消费成功；
  它自己抛异常时附加为 suppressed，保留原始失败。解析失败遵循同样原则。
- 重连仍使用安全快照。业务失败可能重复重放并持续失败，应有结构化 lastError；
  首版不增加自动跳过或按异常文本猜测业务是否可重试。
- 10 秒重试间隔和既有次数配置保留；明确计数是连续连接失败预算，不是业务
  异常总数。终止性错误（ACK 预算溢出、不可迁移、数据范围不存在）不走内部重试。
- start 在启动线程前原子占用状态，防止并发两次启动。工作线程 finally 记录退出
  原因、关闭资源并进入可 reset 状态；外部 stop 等待工作线程退出，回调内 stop
  只请求停止、不等待自己或其他回调，避免死锁。
- resetService 恢复为可用兼容入口：仅在线程已退出时重置运行状态，保留已确认
  恢复位置和订阅配置，清理未确认缓存/旧代次；再 start 使用该安全快照。
  运行中或回调内 reset 明确拒绝；重复 reset 幂等；不得把进度恢复到初始化时间。
- 多分片中的任意一个连接退出时，协调关闭并等待其余连接、冻结各分片快照，
  再启动下一代，避免旧分片继续投递。这个生命周期约束同时覆盖 DRC 和 DTS。

## 7. 上限、日志与观测

不恢复 SINGLE_SERVICE_MAX_PENDING_ACKS=10240，不把正常业务缓冲深度绑定到
隐含阈值。单订阅不需要显式 ACK pending；多订阅使用压缩 ACK 区间，内存仍与
乱序区间数和业务持有的对象有关。

保留建议参数 `client.maxPendingAckRanges`，非负整数，默认 0（不设置隐式上限），
正数按逻辑分片限制多订阅区间元数据，DRC/DTS 同样生效；单订阅没有这些区间。
限制在合并和前缀推进后检查，
等于上限允许。资源预算不是 ringbuffer 容量或 poll 条数。

与上一轮实现的区别：显式预算超过上限时，保留最后安全快照、标记 FAILED、
输出 ERROR，通知协调器停止所有拉取线程；终止内部自动重试，start 返回的线程
最终退出。触发溢出的 ACK 抛专用运行时异常，同时必须通知拉取线程，不能只在
用户异步线程里抛异常。不得保持“冻结位置但持续投递”的状态。

多订阅 ACK 停滞提醒先使用内部 60 秒阈值，不新增告警配置参数：有未确认交付且确认前缀
在这一时长内未推进时限频 WARN。使用单调时钟计算，恢复推进时重置提醒，
无待确认数据不报。纯告警不擅自重连，不改变确认策略，不把重复 ACK 算作进展。

状态快照在 stop/异常退出后仍可查询：ackRequired、channel、
generation、receivedCheckpoint、confirmedCheckpoint、recoveryCheckpoint、
pendingCount、pendingAckRangeCount、progressAge、recoveryProgressAge、lastError、
终止/回退原因。progressAge 衡量确认前缀停滞；recoveryProgressAge 衡量实际恢复
边界停滞，两者分开以识别 DRC 长时间没有合格心跳的情况。
原 getCheckpointStatus 增加字段保持兼容；多个分片不是全局原子快照。
初始化及通道切换日志明确版本、通道、订阅方式、是否依赖 ACK 和恢复选择。

缓存批量参数是阈值，不一定是实际单批硬上限；不能在升级文档把
“ringbuffer 容量 + maxNumOfRecordsPerMessage”写成任意流水线的普适硬上界。
异步使用方应按全部队列、批次、并行度和最大事务控制在途量，成功后再逐条 ACK。

## 8. 实施顺序和现有改动处置

1. 保留并独立验证已有的无注册/重复 ACK 安全性、连续前缀、去 10240 默认条数
   上限、ROLLBACK、无事务标记 DML、线程退出和关闭竞态修复。
2. 以启动方法为固定契约，实现单订阅批次成功返回后的推进；DRC 使用合格心跳，
   DTS 使用批次事务安全边界。两种多订阅使用 ACK 连续前缀；不新增模式参数。
3. 同步修正 notify/解析异常传播、缓存代次、DRC 多分片退出协调、reset/stop 状态。
4. 改显式预算溢出为可见终止，补齐状态/告警、跨通道回退与错误信息。
5. 更新示例、旧手册迁移说明和设计文档；按版本说明已实现与未覆盖的语义。

上一轮还需调整：DRC 单订阅 ACK 保持 no-op，但心跳推进需经过成功交付。
DRC 多订阅保留业务 Record 的链表改用压缩结构。DTS 单订阅从逐条 ACK 跟踪改成
回调成功后的批次确认；原单订阅 ACK 回归测试需按新契约重写。示例分为单订阅
回调完成业务、多订阅逐条 ACK，统一说明异步使用边界。区间溢出继续投递的策略应替换。已有旧设计文件在实施后同步
更新，当前暂保留为实现现状记录。

不新增其他依赖，不改变公开方法签名，保持 Java 8 和既有序列化兼容。具体内部
类拆分和命名留给实施者，完成判据、通道规则、失败行为不留给实现阶段猜测。

## 9. 验收要求

- 四种通道/订阅组合；正常消费、回调失败、内部重连、reset，不新增模式参数。
- DRC/DTS 单订阅均不 ACK，恢复位置随成功交付推进；调用 ACK 无异常且不能
  提前推进；回调抛异常、单批超过 10240、业务修改 Record/列表均不破坏候选快照。
- 两种多订阅中，未 ACK 不推进；延迟 ACK、并发、乱序、重复 ACK、旧代次 ACK
  不越过缺口，回调返回和超时均不能自动确认；仅一个 subTopic 仍遵守此规则。
- DRC 心跳进入缓存但未交付时不可恢复到该处；合并区间右端不是心跳时仍正确
  保留心跳候选；无心跳、心跳时间戳回退、事务 BEGIN/COMMIT/ROLLBACK。
- 空 handleException、handleException 再次抛异常、解析失败、多分片单路失败，
  均不会继续把失败代次的后续数据当作已确认。
- 8192/16384/32768 在途窗口，长期不 ACK 不由 manager 持有全部 Record；区间
  预算恰好等于上限允许、超过后终止且状态可查，不发生静默冻结继续消费。
- 旧同实例 start/join/reset 循环、外部 stop、回调内 stop、并发 start/reset，
  不回退已确认位置，不残留继续投递的旧连接，不因互相 join 死锁。
- DRC→DTS、DTS→DRC、分片拓扑改变，验证完成判据仍由启动方法决定、保守回退事件、无安全
  可迁移时间戳时报错；不拿最新 received 位点当迁移恢复位置。
- 旧 DRC 单订阅不 ACK，切到 DTS 后成功回调仍推进完成位置，不因没有 ACK 长期
  停在旧位置；多订阅在任一切换方向上都等待 ACK。
